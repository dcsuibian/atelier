# 前端本地存储

适用于 `atelier-ui`。往浏览器里存东西，比如让页面记住上次的选择时，看这一篇。

## 只存丢了也无妨的东西

- 存的是偏好和界面状态：主题、语言、菜单折叠、打开的标签页。丢了就回到默认值，不影响使用。
- 登录态、权限、业务数据不往本地存，以服务端为准。

## 小的放 localStorage，大的放 IndexedDB

- 一个开关、一个日期、几个字段的偏好，放 localStorage：同步读写，用起来最简单。
- 成批的数据、缓存的计算结果，放 IndexedDB：读写不卡页面，能直接存对象和二进制，容量也大得多。
- 不用顾虑 localStorage 的总量上限。小项再多，加起来也远到不了上限；真快到了，说明有大数据放错了地方。
- 为什么不全放 IndexedDB：它只能异步读。主题这类偏好要在页面渲染前就拿到，异步读会先按默认样式渲染一次，再闪一下变过来。

## 所有键集中登记

- 存了哪些键，集中写在一处，localStorage、sessionStorage、IndexedDB 都算，不在页面里随手起名。
- 为什么：一眼就能看出应用往浏览器里存了什么，清理、排查都有据可查；新加键时也能看到有没有重名。
- 键不加应用前缀。存储按源隔离，各应用部署在各自的子域名下，天然互不干扰。几个应用共用一个域名时，再在登记处统一加上。
- 坑：改键名等于丢掉用户已存的数据，旧键也会一直留在浏览器里。

## 存 JSON，且只存简单值

- 一律存 JSON 序列化后的结果。直接存字符串的话，布尔值 `false` 读回来是非空字符串 `"false"`，在条件判断里成了真。
- 只存简单值，或者每个字段都是简单值的平铺对象。嵌套越深，读回来时要检查的就越多。

## 读的时候不信任存的内容

- 存的内容可能来自旧版本，可能被用户或浏览器插件改过，也可能干脆坏了。
- 解析失败、类型对不上，就当没存过，用默认值。不抛异常，不登出，不清空整个存储。
- 版本跟着数据结构走，不跟着应用版本走：加字段、删字段都不用处理；只有某个字段的含义或类型变了，才给那一项加结构版本号，对不上就丢弃或迁移。
- 为什么不按应用版本区分：每次发版，存储结构大多没变。按应用版本换键，要么每次升级都白白丢掉用户的设置，要么把旧数据原样复制过去，那版本号就形同虚设。
