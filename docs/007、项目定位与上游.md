# 项目定位与上游

atelier 是什么、不是什么，以及它和 Art Design Pro（下称 ADP）的关系。想大改结构、跟进 ADP 新版之前看这一篇。

## 是模板，不是库

- 不做成 npm 包。库要求接口稳定、发版、使用方跟着升级；模板接受重复代码，换来每个基于它的项目都能完全自主地改。
- 只有小而独立的功能点适合做成库。
- 基于它的项目靠对照 diff 同步，不是 git merge。所以目录结构、文件命名、文件内的顺序尽量保持稳定、便于逐文件对比，不为了更优雅另搞一套组织。
- 坑：同步要有锚点，否则每次都得全量对比。atelier 要打 tag，让基于它的项目知道自己对齐到了哪一版。

## 带一个真后端

- 接口设计的好坏，只有在真实实现里才会暴露：分页怎么传、错误怎么返、鉴权怎么挂。Mock 只能模拟已经想清楚的接口，逼不出这些问题。

## ADP 只作参考，不跟着升级

- 不整目录替换升级，也不建上游分支做三方合并。改得越深冲突越多，不如读 ADP 的版本间 diff，理解意图后自己写。
- 值得跟进的是视觉组件（布局、卡片、表格外观）。路由、表格、图表这类机制层与作者的偏好不合，已经自己接管。
- 坑：要记下对齐到了 ADP 的哪个版本。下次只需看这个版本之后的 diff，锚点一含糊就会退化成全量对比。

## ADP 原件放在 `art/` 里

- ADP 的原件放在各目录的 `art/` 子目录下，自有代码平铺在目录根上。哪些是 ADP 的一眼就能分清。
- 文件名和自有代码一样用 kebab-case，不保留 ADP 的原名。逐文件对照时按目录对应，多看一眼文件名就行；同一个仓库里两套命名规矩并存，代价更大。
- 在原件上的小改动标 `atelier：` 注释，写清改了什么、为什么。跟进 ADP 新版时，搜这个标记就能找全自己动过的地方。
- 改到要重写的程度，就挪出 `art/`、按自有代码的规矩命名，原件直接删掉。留一份用不到的副本，只会让人困惑到底该改哪个。

## 公开，但不是开源项目

- 仓库公开，但不做宣传、不接外部贡献，也不承诺语义化版本或向后兼容。所以没有贡献指南、issue 模板这类东西。
- 坑：ADP 是 MIT 许可，衍生作品必须保留原版权声明。清理上游痕迹时，别把前端目录里 ADP 的 LICENSE 删了。
