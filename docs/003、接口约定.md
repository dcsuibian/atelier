# 接口约定

前后端之间的约定，写接口、改异常处理、写调用方的判断逻辑时看这一篇。

## 两层状态码

- HTTP 状态码回答的是协议层面的问题：请求有没有到达一个接口、被它处理。接口处理的结果放在响应体的业务码里，业务码借用 HTTP 状态码的数字和语义。
- 所以接口处理了请求，不论成功还是失败，HTTP 状态码都是 200。接口不存在、请求方法不支持，才返回真实的 404、405。
- 后端只保证两件事：成功一定是 200；失败时 4xx 与 5xx 不会错位。细分码尽力而为，比如 401 与 403 混用不算缺陷。
- 因此调用方只按「成功 / 失败」分支，细分码留给人排查问题。

## 未登录走真实的 401

- 未登录是唯一返回真实 HTTP 状态码的业务情况，这样前端在 HTTP 层拦一次就够了。响应体仍是统一包装。
- 401 的意思是服务端已经断定没登录，没有按场景处理的余地，所以在 HTTP 层统一登出，不交给各调用点，否则必然有漏的。
- 坑：
  - 一个页面往往同时发出好几个请求，会话过期时它们会一起 401。要去重，只提示、登出一次，否则会连弹好几个「会话已过期」。
  - 查询当前会话的接口在未登录时返回 200 和空用户，不返回 401。否则应用启动时判断登录态，就会触发「会话过期」的提示和登出。

## 会话用 Cookie

- 这是适合浏览器后台的实现方式，不是规定。换成小程序这类没有 Cookie 的客户端时，在 header 里传 token 是合适的。
- 不论哪种方式，都不建议用 JWT：它做不到把人踢下线，要踢就得在服务端存状态，又绕回了有状态会话。有状态会话放在 Redis 里，扛得住很高的并发。
- 坑：Cookie 会话要求前后端同站。前端经反向代理访问后端时没有问题；分开部署在不同域名时，要处理 CORS 的 credentials 与 SameSite。

## HTTP 层不自动重试

超时的请求，服务端可能已经执行过，对新增这类不幂等的请求重试会重复提交。该不该重试，只有调用方知道。

## 时间用毫秒时间戳

- 时间戳是绝对时刻，没有时区歧义；它是整数，各种语言都好处理。按用户所在时区展示是前端的事。
- 不像大整数 id 那样转成字符串传：JS 的 number 能精确表示到 2^53，换算成毫秒时间戳约到公元 28 万年。
- 坑：
  - 别和秒级时间戳混用，很多语言和工具默认给的是秒。
  - 只有日期、没有时刻的值（如生日）不适用。它没有时区可言，转成时间戳后换个时区看可能差一天。

## PATCH 里 `null` 表示不修改

- 反序列化之后分不清「没传」和「传了 null」，所以约定 null 就是不修改。
- 代价是 PATCH 没法把可空字段清空。真要清空，用 PUT 覆盖整个资源，或对那个字段单独 PUT。

## 分页

- 页码从 1 开始，与界面上的分页器一致，前端不用到处加减 1。
- 不返回总页数：它能由总条数和每页条数算出来，冗余的字段可能与原始数据对不上。
- 坑：Spring Data 的 `Pageable` 页码从 0 开始，用它时要换算。

## 前端默认不对密码做哈希

密码明文经 HTTPS 传输，后端直接 BCrypt。前端先哈希再传是可选做法，好处只有一个：后端或网关不小心把请求体打进日志时，留下的不是明文。它不增加传输安全，哈希值本身就成了密码。

要做的话注意：

- 算法用 SHA-256 的 hex。SHA-512 的结果超过 BCrypt 的 72 字节上限。
- 算法和盐上线后就换不掉：库里存的是对哈希值的 BCrypt，换了所有人都得重设密码。
- 盐不是秘密，构建产物里看得见。它的作用是让同一个密码在不同站点得到不同的哈希，建议每个项目各配一个。
- 后端看不到明文，密码强度只能在前端校验；登录接口的所有调用方都要做同样的哈希。
- 用纯 JS 实现，不用 Web Crypto。Web Crypto 只在 HTTPS 或 localhost 下可用，局域网 IP 走 http 访问时用不了。
